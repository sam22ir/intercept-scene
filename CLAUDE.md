# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Interactive Three.js scene: an orange target drone is launched off a side rail (18°) with a rocket booster under its tail, on a steaming stealth frigate (C28A style, pennant 920). It flies a loop, makes a low close pass along the port side, climbs out slowly ahead, then turns back for an inbound run at the ship. On that run, a missile from the frigate's forward box launcher shoots it down. The user can scrub time forwards and backwards and click the drone, missile or ship to focus the camera on it. Vanilla JS (ES modules), Vite, `three@0.186.1`. Node regression tests for `scenario.js` (`pnpm test`, also run by `pnpm build`); no linter.

Catch undeclared variables (a runtime error the build and tests miss) with `npx --yes eslint@9` and a flat config that turns on only `no-undef` (browser globals declared), run over `src`.

The folder name ends with a **trailing space** (`/home/saadi/plane sceen `). Quote every path in shell commands.


`scripts/build-offline.mjs` runs after `vite build`. It inlines the single JS bundle and the CSS into `dist/intercept-offline.html`, which opens by double-click from disk with no internet. The site links to it ("Download offline version", `#dl-offline`), and the script strips that link from the offline copy. Keep the app free of runtime network loads (fonts, CDN scripts, fetched assets) and of code splitting, or the offline file breaks. The script fails the build if it finds more than one bundle.

Live at https://intercept-scene.nafaa-store.workers.dev. The owner has asked that every finished, tested change is pushed and deployed straight away, without asking first (deploying is public, so run the tests and the build first, and do not deploy if they fail): `git push`, then `node scripts/build-offline.mjs` after `vite build`, then `npx wrangler@4 deploy` (pnpm and a local wrangler are not installed on this machine).

`src/scenario.js` imports only `three`, so timings and clearances can be checked in Node without a browser. Import it and sample `planeRelPos`, `missilePos` and `shipPos`.

To test in a real browser, use the built-in browser pane (`preview_start` with the `dev` entry, then the `mcp__Claude_Browser__*` tools); do not drive headless Chromium with Playwright. Load a scene with `?mode=…&start=1`, seek with `__scene.clock.seek(t)` through `javascript_tool` instead of waiting for real-time playback (software rendering is slow, 1-2 fps), then screenshot. In the browser console, `window.__scene` exposes `{ scenario, clock, setFocus, camera, controls, rig, renderer, plane, missile, ship }`, for example `__scene.clock.seek(__scene.scenario.tHit)`.

## Missions

The start screen also picks the mission (`?mode=intercept|chute`, or `globalThis.__SCENARIO` set by `start.js`, read once at import like the ship variant):
- **`intercept`**: the missile shoots the drone down on its inbound run, as described below.
- **`chute`** (recovery): the missile is never fired and nothing is hit. At the end of the planned path (`T_CHUTE`) the engine cuts and the drone opens a red square parachute, descends and lands in the sea.

- The **Two drones** mission (`pair`) was removed. `scenario.engagements` (length 0 in chute, 1 in intercept) and `scenario.drones` (length 1) are still lists, and `planePos/planePose/planeVel/propAngle/missilePos/missilePose/tubeMouth` still take an optional last index `k`, always 0 now.

In recovery mode `tLaunch` and `tHit` are `Infinity` so every `t < tHit` check stays true. The missile simulation, debris, fireball and launcher aiming are skipped (`scenario.hasMissile` is false, `debris` is `null` in `main.js`, and the missile focus button is disabled). Code that loops up to `tHit` must use `scenario.tChute` instead (see `tFlightEnd` in `effects.js`). The default path is the intercept path cut at the middle of the inbound run, and a custom path is stored under its own key (`intercept.path.chute.v1`).

## Naval maneuvers mission

The **two-ship drill** is the briefing deck alone: the same orders and trajectories up to FORM 120 (the unit never affected ALG or RUS there), then **FORM 345** (ALG, the guide, comes to 090 at 6 kn; RUS is steered by `steerStations` to true bearing 345 from ALG, 500 yds, laid off from ALG instead of the unit (`REF_FULL`, `STEER_IDS`), which is where the serials and the skim start from), then the light, the flags, the skim and the close pass (100 m): 12 orders, about 36 minutes, no unit, no formations on her, no screens, no `PASS_UNIT` (null). Its later phase times are the `t2` fields (each order 40 s after the last arrival). In the two-ship drill FORM 345 is shown as an ordinary station from the guide (`STATIONS.form345`; the exported `FORMS` is empty, the steering uses the internal `FORM_STATIONS`). `test/maneuvers2.test.mjs` checks it.

The three-ship drill, after the "Tactical maneuvers" briefing deck: two frigates, ALG and RUS (and a larger unit following astern), in FORM 1 (a column, 500 yds apart (`STATION_YD`; the deck says 1000, the scene keeps the ships closer so both read on screen, and the runs `G1 G2 F_C F_T` were re-solved for it; the skim U-turn is then 1.6 deg/s), heading 315) run through the deck's slides: CORPEN STBD 4 ANS (a wheel in column to 000, right after FORM 1), turn stbd 90 and port 90 together, G FORM RUS (RUS passes ALG to port and takes station ahead), turn 045, FORM 120, a flashing-light serial, a flag-hoist serial, and RUS skimming past ALG at about 100 m on a reciprocal course. No drone, no missile. It has its own scene: `start.js` imports `src/maneuversMain.js` instead of `main.js` (and hides the ship step, since both ships are fixed).
- `src/maneuvers.js` is the pure model (imports nothing, tested in Node by `test/maneuvers.test.mjs`). Coordinates: x North, z East, heading in radians clockwise from North; they coincide with the scene axes, so a ship's group is `rotation.y = -heading`. **Both ships steer by real orders** (`ALG_ORDERS`, `RUS_ORDERS`: course, speed, turn direction), integrated once into 0.25 s tables with a 1.2 deg/s turn rate and 0.08 m/s^2 acceleration, so `shipState(id, t)` is a pure function of `t`. Speeds are the deck's: 6, 10, 12 and sierra 15 kn. The station changes are turn-and-runs whose courses and times (`G1`, `G2`, `F_C`, `F_T`) were solved offline with a grid search over the same integrator, so each ends within a few metres of the deck's station (G FORM RUS: ALG slows to 6 kn, RUS runs 340 then 020 at 15 kn, passing 520 m to port; FORM 120: RUS drops back at 6 kn; CORPEN STBD 4 ANS comes right after the FORM 1 stations and is a **wheel in single column** (Vol. II 700a(1)): the column starts on `START_COURSE` 315, ALG (the leader and guide) wheels to 000 and RUS follows round in her wake, turning `WAKE_DELAY` (one station at 12 kn) later at the same point, so everything after it runs from the deck's base course 000 unchanged. (A wheel in line abreast or on a bearing would instead keep the gisement and distance, the outer ships speeding up; that is not used here.) TURN STBD 9 / PORT 9 / STBD 045 are turns together: both put the rudder over at once, the true bearing between them unchanged). **Changing a speed, a turn rate or a phase time means re-solving them**; `test/maneuvers.test.mjs` fails if a station drifts. The `PHASES` array mirrors the slides: title, start time `tx` (the ships start to obey then, so every trajectory hangs on it), announce time `t = tx - STANDBY`, arrival time `ta`, the serial text and a `note`. **The standby time is a setting** (`STANDBY`, 3 to 25 s, default 10, `localStorage['intercept.standby']`, or `globalThis.__STANDBY` in tests; read once at import): it is the warning before the ships start moving and only moves the announcements, never the ships or their arrival (`test/standby.test.mjs`). The stepper at the foot of the Orders dropdown changes it and reloads the scene at the same moment (`sessionStorage['intercept.seek']`, `intercept.skip`); the first order executes at 25 s so even the longest standby fits after the start. `orderStatus(t)` gives an order's stage: idle, **standby** (only getting ready: the ships do not move, and the count runs to EXECUTE at `tx`), **execute** (`EXECUTE_FLASH` s from `tx`, when the ships start the maneuver), **underway** (maneuvering; `count` is the time to `ta`), **station** (`STATION_FLASH` s from `ta`: the **A STATION** call, when the ships have reached the ordered position) and **onstation**. `ta` is the deck's time of arrival, found from the ships' own motion (the first moment after which they stay on the ordered course and station for 10 s, `ARRIVAL`; a serial arrives when it ends, the skim at the pass). Orders that only signal (the start and the FORM 1 stations) have `hasStation: false`: they execute and are done, with no under-way or A STATION part. `lampOn(t, id)` is the signal lamp's dot-dash pattern and `CUES` the sound cues (one long horn blast from ALG at each EXECUTE, RUS and then ALG at the close pass, a click per lamp flash). ## Four-ship formations mission

A mission on the start screen after the drill (`?mode=formations`): four frigates, SHIP1 to SHIP4, run the tactical formations with wheels and turns together between them, and nothing else (no signal serials, sound, drone or missile). 11 orders, about 37 minutes, 8x: FORM 1 (column, 000), CORPEN STBD 9 (the column wheels to 090), FORM 225 (line of bearing on the starboard quarter), FORM 3 (line abreast), TURN PORT 9 and TURN STBD 9 (turns together: the line abreast becomes a column on 000 and back), BOX, CORPEN PORT 9 (the box wheels to 000), FORM 1, FORM D (diamond), CORPEN STBD 9 (the diamond wheels to 090). 500 yds between neighbours as ordered and shown, but the ships sail at `SCALE` (0.5) of every ordered distance so a whole formation reads on screen (as the drill does); every number shown is in ordered yards (`orderedYd`), and the sea-metre tolerances (`ON_STATION`, `KEEP_CLEAR`, `STAND_ON`, `T_CROSS`) scale with it; designators from the MTP 1(D) Vol. II notes above (the box has none). `start.js` imports `src/formationsMain.js`.
- `src/formations.js` is the pure model (imports nothing, `test/formations.test.mjs`). SHIP1 is the guide at 12 kn on the ordered course. `FORMS` gives each ship's station in yards ahead / to starboard of her on the formation axis (a FORM order takes the present course as the axis). The station plan `phase.S = { form, mode, axis }`: in `track` mode (FORM and CORPEN) a station `a` yards astern is the point the guide passed `a` yards ago, laid off `s` yards square to her track there, so in a CORPEN the column follows round in her wake and a ship abeam runs faster outside the wheel and slower inside; the wheel rate (`phase.rate`) is the guide's 1.5 deg/s cut so no ship needs more than 20 or less than 5 kn (`WHEEL_MARGIN`). In `fixed` mode (TURN) the stations stay rigid on the old axis and every ship simply turns to the new course at the same rate, so the true bearings do not change. The followers close their station error with a proportional law on the station's own velocity (`T_CROSS`, at most 50 degrees off it, 5 to 20 kn, 1.5 deg/s, 0.12 m/s^2) plus a keep-clear push inside `KEEP_CLEAR` (the guide never gives way), baked once at 0.25 s. A ship whose new station lies on her own line when a FORM executes (within `STAND_ON`, 50 m: SHIP2 into the box, SHIP3 box to line ahead, SHIP4 into the diamond; `phase.standOn`) is the stand-on ship: she keeps the course and only changes speed, and the others keep `STAND_ON_GIVE` (3) times further clear of her. A give-way ship whose new station is across a stand-on ship's lane or in it (`LANE`, 150 yd) waits for her (`phase.waits`: SHIP3 and SHIP4 for SHIP2 into the box, SHIP4 for SHIP3 box to line ahead): she holds the course and changes speed only until she is `PASS_CLEAR` (250 yd) past her along the course, then turns in. Orders are scheduled by the ships' own motion: arrival `ta` is every ship within `ON_STATION` (40 m) and `ON_COURSE` (2 deg) for `ARRIVAL` s (in track mode also only once the rearmost ship's track point is past the turn plus `ARRIVAL`), and the next order executes `HOLD` (60) s later, so changing a gain, speed or station moves every later order (the tests check stations, courses, speeds, a 250 m minimum separation, the wake, the turn together and the schedule).
- `formationsMain.js` wears the drill's look and layout (`body.mission-maneuvers` plus `mission-formations`): its order and ships cards (`mcard`, `mh-*`), the vertical timeline and camera strip, the EXECUTE / A STATION call, station rings in each ship's colour, wakes, dotted tracks, tags and its own north-up map in `#minimap`, centred on the guide SHIP1 (fixed in the middle, as in the drill). Cameras: SHIP1 to SHIP4 (1 to 4) and Formation (5); the Formation view is the drill's (`applyFormationView`): behind and above the other three along SHIP1's heading, looking at them, turning as she turns and pulling back with their spread (farther on a tall window); OrbitControls are off there, drag swings round, the wheel scales the distance (`formZoom`), double click resets. The ships sail close, so `declutterTags` (run each frame after the camera moves) lifts a tag that would overlap another on screen and stretches its stem (`--lift`); the banner says the short order label (it is the map's width); between 901 and 1099 px (a 1920 px screen at 175 % scaling) the camera buttons take their own row in the playback panel so it stays clear of the map. It does not share the drill's names, grid, sound, orders or signal dropdowns.

## Fly the drone mission (manual flight)

A fifth mission on the start screen (`?mode=fly`): you fly the drone. **It is the one place the core rule does not hold**: nothing is a pure function of a clock, because a flown drone cannot be rewound. There is no timeline, trails or tags; the map (`src/flyMap.js`, **M**, click to zoom) is bow up and centred on the drone, with the ship, the drone's two-minute track, the missile and the wreck, and zooms out to keep the ship in view (at a fixed zoom a marker on the rim points to it); the sim runs in real time and R starts again. `start.js` imports `src/flyMain.js` and sets `__SCENARIO = 'chute'` (so `scenario.js` simulates no scripted missile; the ship is always the `fwd` fit).
- `src/fly.js` is the pure model (`FlySim`, tested in Node by `test/fly.test.mjs`), stepped at a fixed 1/240 s so it behaves the same at any frame rate. Phases: `deck` (on the cradle, engine off) → `cat` (the scenario's own short stroke (3.6 m, about 0.28 s, 26 m/s off the rail), `RAIL`, `tSpool`/`tRelease`) → `flight` → `chute` → `splashed`, or `crashed` (sea, or the ship's boxes, `insideShip`) or `destroyed` (the missile). **E** starts the engine only on the ship (3 s run-up as in the scripted launch) and in flight cuts it for good: the parachute opens by itself (the recovery mission's descent, rebuilt from the real state at the cut: `descentRaw`, bisection for the splash time) and it can never be restarted. **L** fires the catapult once the engine is at full power (pressed earlier it arms and fires as soon as it is). **Arrow keys**: left / right bank to 75 degrees (3.9 g; 28 degrees a second and a 150 m radius at 75 m/s) and turn at g tan(bank) / v (a coordinated turn; the roll follows the key in 0.22 s), up / down pitch to +30 / -25 degrees; the cruise speed is **75 m/s** (`[` `]` change it, 45 to 110, `localStorage['intercept.fly.speed']`); the booster adds 36 m/s² for 1.2 s after release. The drone's world velocity is the air velocity (no wind); the ship moves at `SHIP_SPEED` along +X.
- **F** fires the frigate's missile at the drone (two rounds per run, one at a time, 4.5 km range, also at a drone under canopy or floating): the launcher slews for 1.6 s toward the predicted position (pitch 25 to 70 degrees as in `aimFor`), the round leaves the cell, and homes by the intercept mission's proportional navigation (N = 5, 60 g limit, speed profile 40 to 420 m/s), re-run live against the drone's real velocity, fuzing within 3.5 m. It is lost after 12 s or in the sea.
- `src/flyMain.js` builds the scene like `maneuversMain.js` (same environment, ship, plane, parachute and missile models), steps the sim each frame and turns its events (`takeEvents()`: say, launch, release, chute, splashdown, fire, explosion, crash, missile-lost) into effects. Hooks added elsewhere: `ship.update(t, tFire0, tFire1, { aim, cradleT })` (a launcher aim and cradle clock the pilot controls), `createDebris(plane, k, hit)` (a wreck from an explicit hit state), `env.follow(camPos)` (the sky dome and WebGL sea ride with the camera and the clouds wrap, so a far-flying camera never reaches the edge of the world), and `scenario.tChute` / `tSplash`, which the parachute model reads and this mission sets at the moment of the cut (both are `Infinity` until then: the recovery scenario's own scripted time must never open the canopy).
- `src/fx/liveFx.js` is the runtime counterpart of `effects.js`: `ParticleField`s written as things happen, into ring buffers (the oldest particle is overwritten), against the mission clock: the booster plume and deck blast, exhaust haze, the missile's smoke trail, the launch billow, the fireball with flash and light, burning smoke along the falling wreck, splashes and foam rings. The camera is a chase camera that turns with the drone (the heading is smoothed, the position is not, so there is no lag along the path); **V** cycles chase, orbit (`CameraRig` on the drone) and tower. The readouts are the usual `#hud` panel, the keys for this moment sit in `#fly-keys`, and the banner (`#shot-caption`) shows the model's messages. Sound (`src/flyAudio.js`, the Sound button and **S**, remembered in `localStorage['intercept.sound']`, `test/flyAudio.test.mjs`): the same embedded samples as `audio.js`, but driven live instead of from a timeline: the engine loop pitched by the prop (`sim.spin`) and airspeed, the booster and missile-motor loops, ship hum, wind from the airspeed and surf from the height, all Doppler-shifted by their speed relative to the camera (which moves with the drone in the chase view), and one-shots started by the model's events (catapult hiss, release clunk, missile launch, explosion, splashes; the wreck's fuselage splash is scheduled for when it reaches the water). The context starts at the first key press or click.

## Ship duel mission

Mission `duel` (Play tab, `?mode=duel&level=easy|normal|hard`, the enemy's level set by `start.js` in `globalThis.__DUEL_LEVEL`, read once like the ship): you sail a frigate against an enemy frigate that sails herself, 76 mm bow gun and two aft 30 mm guns each, until one sinks. It has its own scene, `src/duelMain.js`, over a pure real-time simulation, `src/duel.js` (imports only `hull.js`; seeded; tested in Node by `test/duel.test.mjs`).
- **`src/hull.js`** is how a frigate handles (`stepHull`: wheel, telegraph, Nomoto turn, heel), plus the aft guns' mounts and dead zones and the bearing helpers. Solo Air Defense (`helm.js`) and the duel share it; the duel passes a wider `radius` (120 m against helm's 70).
- **The mechanic is manoeuvring, but honestly it is modest**: both ships' guns train by themselves, the fire control predicts the target's straight-line motion for the shell's time of flight from a velocity estimate that lags (`track`, 3 s for you, by level for the enemy), shells are ballistic (650 m/s, 8 km) and hit by a segment test against the hull in its own frame, and scatter grows with range and with the firing ship's own turn rate. Measured with scripted players, presenting the bow beats presenting the beam, and each level up hits more; weaving alone barely helps because the hull is big. Tune by play-testing.
- Difficulty (`LEVELS` in `duel.js`) changes only the enemy's decisions and aim (think interval, scatter multiplier, tracker lag, preferred angle off her bow, jinks, range, retreat), never the physics. `new DuelSim({ seed, level, auto })` can hand the player's ship to the same helmsman for tests.
- **Damage**: hull points and five compartments (76 mm gun, bridge, engine, steering, aft guns), assigned by where along the hull a hit lands (`zoneAt`). Each has one effect (slower load, more scatter, speed cap, rudder limit, guns out); a compartment that is out floods the ship; at zero hull she sinks by `sinkState(age)`, a closed form the scene draws.
- **Scene**: `createShip({ crew: false })` for both ships (the deck crew stands in the gun's way); `createShip().mainGun.pose(yaw, pitch)` turns the 76 mm (the turret was merged into the static geometry before, and now follows reference photos of the real turret); a wake per ship from `fx/wake.js` (extracted from helmMain, shared); `liveFx.shellBurst` / `fireSmoke` for hits and fires. Views 1 to 5: behind, bridge, above, orbit, radar (the long-lens sight and the shell camera were removed). Keys: arrows, F (76 mm, hold), G (30 mm, hold), A (auto 30 mm), R, N, H, S.
- **Depth systems** (all in `duel.js`, same rules for both ships, no missiles: those belong to Solo Air Defense): **HE and AP rounds** (`AMMO_STOCK` 90/60, key **Q**, `switchAmmo` costs `SWITCH_TIME`; HE starts fires and leaks, AP hits one compartment harder); **fires, leaks and 3 repair crews** (`CREWS`, `assignCrew`, keys **Z** picks a compartment and **X** sends or recalls a crew); **manual aim** (**T**, `setManual`: the pointer's ray meets the vertical plane through the enemy and `sim.solve` gives yaw and pitch for that still point, so you judge the lead; scatter `MANUAL_SCATTER` 0.6x; in manual mode with no aim the gun holds and cannot fire). The enemy picks ammo and crews by level (`ammo`, `crews` in `LEVELS`). A duel lasts about 2 to 5 minutes (`test/duel.test.mjs` checks the mean); holding F against Normal loses at least 10 of 16 seeds. The radar is `src/duelMap.js` on the shared `#minimap` (heading up, 76 mm arc).
- **Radar view = aimed fire at a compartment**: key **5**. The sight's lens zooms (wheel, **+** / **-**, **Shift** in and **Ctrl** out, the lens track, **0** resets; `sightZoom`, lens 0.3 to 30 degrees) until a compartment fills it. Every enemy hull shows its five compartments as marks (name and health once they are 80 px apart on screen); a click on one **locks** the sight on that point of the hull (`sight.lock`, held as she sails; Enter locks the point under the crosshair, arrows, a drag or Space let it go), on the side of her hull that faces you (`nearSide`: a shell strikes the first face it meets, so aiming at the middle of a bow-on ship would only hit her bow). `sim.solve(..., at)` takes the aimed world point and its velocity (`sim.estOf`), the shell flies there, and `zoneAt` of where it strikes picks the compartment (scatter spreads some into the neighbours: in a stopped-target test about two thirds land in the aimed one). A merchant or friendly ship under the crosshair is not fired on (`input.aim` null: the gun holds). **Locked, focused and free shots** (`aim.lock` / `aim.focus` / `aim.free`): the marks sit where each compartment really is (`ZONE_POS`: turret, wheelhouse, funnel, aft 30 mm mounts, stern). In AUTO the sight snaps to the nearest mark (`sight.snap`) while the marks are on screen (`MARK_MIN` px apart) and holds her middle when they hide. A **locked** shell is led by her true velocity, has `LOCK_SCATTER` 0.1x scatter and takes `LOCK_FRACTION` (25 %) of the compartment's points; a **focused** one (snapped, not locked) lands in the snapped compartment with `FOCUS_SCATTER` 1.5x and takes `FOCUS_FRACTION` (14 %); a **free** one (neither) flies through every hull into the sea. An aim with none of the flags is the plain manual shot. Your ship's status card (`.duel-ship`) stays on screen in the radar view, small, down the left under the top bar. On Easy the enemy frigates that arrive are `passive` (they never fire); the friendly one fights on every level.
- **More ships** (`new DuelSim({ waves: true })`, which `duelMain.js` sets; tests default it off, so a plain duel is unchanged): ships have a `team` (0 yours, 1 enemy, 2 neutral) and a `target` (the nearest living hostile with 25 % hysteresis; **Tab** `cycleTarget` locks one until she sinks; `sim.enemy` is the player's target). `planWaves`: enemy frigates arrive over the horizon (`ENEMY_WAVES` by level, 7.5 km out, and the next is called in at once when the last is down), a friendly frigate (AI at Normal) comes from astern at 95 s, and three merchants (12 kn, unarmed, 70 hp, neutral) cross the line of fire; a stream of its own, `rngW`, picks where, so the gunnery draws are untouched. No friendly fire; a shell from anyone can hit a merchant, and **sinking one with your own guns loses the duel** (`merchantsSunk`, `over: 'merchant'`). Hulls collide (`stepCollisions`: centre-line capsules, damage by closing speed at the compartment where they meet, both slow, 4 s before the same pair can hit again); `test/duelWorld.test.mjs` covers aiming, targets, waves, the merchant rule and collisions. The scene pools a picture per ship (`makeVisual` / `releaseVisual`, `syncShips`), `models/merchant.js` is the container ship, and the radar map draws all of them (red enemy, blue friend, grey merchant, a ring on your target).
- **The bridge (key 2) is Solo Air Defense's wheelhouse** (`models/bridge.js`, eye `HELM_EYE`): the helm wheel turns with the rudder, the two telegraph levers follow the engine order, a drag looks round and a double click looks ahead. The keys hint names the order ("thrust Half").
- **Sound**: `src/duelAudio.js` (beds and the rotary guns from `audioAssets.js` and synthesis) plus three ElevenLabs effects made for it (`duelAssets.js`: gun, hit, sink; the prompts are in its header). A far sound arrives late (distance / 340 s).
- The built-in browser pane cannot run the scene while hidden: `start.js` waits on `requestAnimationFrame`, which does not fire there. Use `?start=1` with the pane visible, or import `/src/duelMain.js` by hand (`window.__duel` exposes the sim).

## Fleet command mission

Mission `fleet` (its own Command tab, `?mode=fleet&level=easy|normal|hard`, the enemy's level set by `start.js` in `globalThis.__DUEL_LEVEL` like the duel): a strategy game from above. You command 3 frigates with the mouse against 3 enemy frigates that command themselves; sink them all before they sink yours. A live simulation like Fly and the duel (not a pure function of `t`: no scrubbing, only pause and 0.5x to 4x speed). `start.js` imports `src/fleetMain.js` and sets `__SCENARIO = 'chute'` (so importing `createShip` does not simulate a scripted missile).
- `src/fleet.js` is the pure model (imports only `hull.js` and `duel.js`'s `DUEL_LEVELS`; `test/fleet.test.mjs`): `FleetSim({ seed, level })`, fixed 1/60 s steps (`advance(dt)` or `step`), `order(ids, cmd, queue)` with `cmd` = `{type:'move', x, z}`, `{type:'attack', target}` or `{type:'stop'}` (only team 0 ships obey; `queue` is Shift), `takeEvents()` (fire, hit, splash, sunk, over). Ships sail with `stepHull` (turning radius 90 m). A **move** helmsman steers by bearing and slows near the goal (done within `ARRIVE_RADIUS` 110 m); an **attack** order closes to the standoff range, then circles broadside to her; with no order a ship holds, and every ship fires by herself at the nearest enemy in `GUN_RANGE` (2,200 m, 3 s between rounds, 9 hp a hit of 100). A move given to several ships sends them in line abreast, `FORMATION_GAP` 260 m apart, in the order they already lie across the line of advance (`formationDests`). Hulls closer than `KEEP_APART` are pushed apart.
- **Gunnery is deliberately simpler than the duel's**: no compartments. A shell takes `d / 650` s to arrive and whether it hits is one seeded roll, worse with range and with the firing ship's turn rate (`WRECK_TURN`), times the enemy level's `hitMul`; a wounded ship (under 35 hp) is slower and aims worse. Levels (`LEVELS`) change only the enemy's decisions and aim: think interval, `focus` (hard: everyone picks the wounded and close), standoff, `hitMul`. Measured with a scripted attacker (attack the weakest, re-ordered only when a target sinks): wins 16 / 12 / 9 of 20 on easy / normal / hard. Fleets start 4,600 m apart on the z axis (yours west, hers east: side by side on screen).
- `src/fleetMain.js` is the scene: the `fly` look (`createEnvironment`), `createShip({ crew: false })` per ship (enemy `ensign: 'rus'`), a wake each, `liveFx` for smoke, bursts and splashes, shells as additive sprites from `sim.shells`. The camera is straight down (a slight tilt), north up (+x), east right (+z), `cam = {x, z, h}`; OrbitControls is not used, so there is nothing to fight the mouse. Everything else is a 2D overlay canvas (`.fleet-overlay`, pointer-events none): selection rings, health bars, order lines, gun range of the selected, order pulses, the selection box and the map (bottom right: click jumps the camera, right-click orders a move, right-drag pans the camera). Pointer handlers sit on `window` and act only when the target is the scene canvas (picking is by screen distance to the ship, since hulls are a few pixels from above). Keys: left click / drag box select (Shift adds), double click all, right click move or attack (Shift queues), Space pause, 1 to 3 pick a ship, E all, X stop, F find, Tab cycles enemies, + - speed, R again, WASD / arrows / middle-drag pan, wheel zoom. `window.__fleet` exposes `{ sim, cam, selected, camera, visuals, restart }`.
- **Smoothness and quality**: the scene renders at 70 % resolution (`RENDER_SCALE`), with a 720 px shadow map and 70 % particle density. Ships are drawn extrapolated by the unspent part of a fixed step (`updateView`, `P(s)`), so motion is smooth at any frame rate; the wheel eases `cam.h` toward `cam.hT`; frame dt is capped at 0.05 s.
- No sound yet. The hidden Browser pane never starts the scene (`start.js` waits on `requestAnimationFrame`): front the tab (`tabs_select`) and use `?mode=fleet&start=1`.

## Engagement settings

The missile engagement can be tuned from the ⋯ menu → Missile engagement (key **G**, `src/engagePanel.js`). The setting is `{timing, time, dist, side}`, stored in `localStorage['intercept.engage.v1']` (or `globalThis.__ENGAGE`, used by tests), read **once at import** like the path, and applied by reloading (the panel's Apply & replay also sets `sessionStorage['intercept.seek']` so the next page opens 4 s before launch, playing). It does nothing in the recovery mission.
- `timing` picks one launch trigger: `auto` (derived launch, the default), `launch` (missile leaves at `time`), `impact` (`solveLaunchForImpact` steps the launch time by the remaining error until the burst lands at `time`) or `range` (`launchAtRange`: the first moment the drone, having been farther out, closes to `range` metres of the ship, 100 to 1500; `auto` is the same search at `LAUNCH_RANGE` = 650). `previewEngagement` reports `rangeOk: false` when the path never closes in from that far.
- `dist` (0 to `MAX_BURST` = 60 m) and `side`: 0 is a direct hit (last missile sample snapped onto the drone). With `side: 'auto'` the warhead fuzes when the missile first comes within `dist` of the drone, on whichever side it arrives. With `above|below|left|right` the missile is guided to a point `dist` away from the drone in its velocity frame (right = velocity x up), and the last sample is snapped onto that point. `engage(k, tLaunch, opts)` returns `burstDist`, and `scenario.hitPos` is the burst point, so the fireball, flash, light and boom sit there, not on the drone. `createDebris` (`fx/effects.js`) throws each part away from the burst point when `burstDist > 0.5`, harder the closer it was.
- `previewEngagement(opts)` reruns one engagement without baking it, for the panel's live launch/flight/impact readout. The HUD debrief shows "Direct hit" or "Burst N m away".

## Ship variants

The player picks a mission and, where it has one, a variant on a start screen (`#chooser` in `index.html`, driven by `src/start.js`, the real entry point). Four tabs sort the missions by what the player does (`GROUPS` in `src/menu.js`): **Watch** (Intercept, Recovery), **Play** (Fly the drone, Solo Air Defense, Surface battle), **Command** (Fleet command, the strategy view)  and **Drill** (the three naval drills, folded into one "Tactical maneuvers" entry, `FAMILIES`, whose variant is the number of ships). `entriesOf(group)` / `ENTRIES` give what a tab lists and the order of the **M** key. The briefing shows an animated preview (`src/menuArt.js`: pure SVG strings, SMIL with one shared 9 s loop and keyTimes windows, a still frame under `prefers-reduced-motion` because CSS cannot stop SMIL, and it imports nothing; the aft preview fires astern at a drone coming from behind) and the variant row: the launcher cards (`[data-ship]`, Watch missions) or the ships picker (`.pick[data-mode]`, Drill). Each mission remembers its own launcher (`intercept.ship.<mission>`), the drill its ships (`intercept.drill`), and the footer marks the last played mission. All are radio groups (`[data-tab]`, `[data-mode]`, `[data-ship]` with `aria-checked`; a hidden row needs the `[hidden]` rule, since `.mission` sets `display`): a click or a key (M, 1/2/3, arrows) only selects, hover is visual only, and the Start button, Enter or a double click launches. `launch()` runs at most once. The screen fits 1092×598 without scrolling (Solo Air Defense's long tagline is the worst case); on phones the Start bar is sticky at the bottom (portrait stacks everything, landscape puts the list left and the briefing right). The `.chooser` grid centres with `margin: auto` on `.mm`, so tall content scrolls instead of being clipped at the top. Nothing inside the chooser may use `.panel` (hidden before `body.playing`), and its class names must not reuse the HUD's (`.seg`, `.tile`, `.opt` already exist there).

- **`fwd`**, pennant 920: launcher on the forward deckhouse roof (the original fit).
- **`aft`**, pennant 921: launcher on the aft end of the hangar roof (it replaces the CIWS there). It fires astern: its drone makes the final inbound run from behind the ship.

The choice reaches `scenario.js` through `globalThis.__SHIP_VARIANT` (set by `start.js` just before the lazy `import('./main.js')`) or, for deep links, `?ship=fwd|aft`. **The page always opens on the start screen (the main menu), whatever the address**: a `?ship=` / `?mode=` in the URL only preselects the choices, and a shared link's moment (`?t`, `?focus`, `?cam`, `#path=`) is kept and applies when Start is pressed. `start.js` goes straight into the scene only for `?start=1` (scripted or headless runs, e.g. `?ship=fwd&mode=intercept&start=1`; `launch()` removes it from the address bar, so a refresh shows the menu again) and after the app's own reloads (path editor Apply / Restore, engagement Apply and the maneuvers' standby stepper set `sessionStorage['intercept.skip']`, which `start.js` reads once). Reloading by hand therefore always returns to the start screen. It is read **once at import time**, so switching ship means a fresh page load: "Change ship" sets a `sessionStorage` flag and reloads so the chooser shows again. Picking a ship does **not** navigate or reload, because navigation fails in sandboxed file viewers and previews. `start.js` also shows a loading screen while the scene builds and an on-screen error box (with a WebGL hint) if start-up or rendering throws. Never touch `localStorage` or `sessionStorage` outside `try`: even naming them throws in blocked-storage and sandboxed contexts (use the `read`/`write` helpers in `start.js`). `main.js` is imported lazily, so `vite.config.js` sets `codeSplitting: false` to keep a single JS bundle for the offline file. **Firing arc rule**: each box only engages a drone ahead of or abeam its pivot (`fwd`) or astern of or abeam it (`aft`), so a missile never crosses the ship (`inArc` in `deriveLaunch`; a test samples the missile in the ship frame). The variants therefore have different default paths: they share the release, loop and close pass, then `INTERCEPT_PATH_AFT` swings round the bow and comes back inbound from astern (a hit about 540 m astern, launch near 68 s; `fwd` launches near 47 s). Recovery uses the forward path for both ships. Custom paths are stored per ship (`intercept.path.aft.v1`), and a custom path that never gets in arc falls back to the old launch times. The aft fit differs in its pivot and stow yaw (facing the stern); `launcherAim` unwraps each aim yaw so the slew takes the short way round. To check a variant in Node, set `globalThis.__SHIP_VARIANT = 'aft'` before importing `scenario.js`.

## Architecture

**Core rule: every visual and every sound is a pure function of the sim time `t`.** Nothing accumulates per-frame state, which is what makes reverse playback and scrubbing work. Any new animation must be computable from `t` alone, including flicker, strobes and flag ripple. A stateful update breaks scrubbing (check by jumping to the end, then back to 0).

### `src/scenario.js`

Holds the story, all timing and every ship mount point. Units are metres. The bow points +X, +Y is up, starboard is +Z. Model noses point along local +Z.

- **Moving ship frame**: the ship moves at constant `SHIP_SPEED`, and `shipPos(t)` is a pure translation, with no roll or pitch. The catapult `RAIL`, `LAUNCHER_PIVOT`/`TUBE_MOUTH` and `deckHeight(x)` are defined in the ship frame. `ship.js` builds its geometry from these same constants, so move a mount here, not in the model.
- **Drone path**:
  - On the rail, the drone strokes in closed form (`RAIL.length` 3.6 m, about the length of the drone's own body, as in the launch photos: `CAT_ACCEL` 94 m/s² for about 0.28 s, so it leaves at about 26 m/s and the booster takes it up to cruise within `SPEED_KEYS`' first 1.3 s; the launcher model in `ship.js` is sized to match and the director's catapult camera sits mid-rail). The booster burns from `tBoost0` (cradle starts moving) to `tBoost1` (1.2 s after release), and the plane model hides the canister shortly after (`plane.setBooster(t, …)`).
  - After release it follows a Catmull-Rom curve in the **ship frame** (`planeRelPos`), driven by a relative-airspeed profile through a precomputed arc-length table. `planePos` adds `shipPos`.
  - The first waypoint and tangent are derived from the rail-end pose, so the release is continuous.
  - Attitude follows the *relative* path; bank comes from turn rate.
- **Recovery descent** (`CHUTE_MODE`): after `T_CHUTE` the drone follows a closed-form world-frame descent. The horizontal speed bleeds off into a breeze, the vertical speed settles to a 5.4 m/s sink rate, and `T_SPLASH` is found by bisection. The attitude blends from the path's last attitude to a swinging hang, then a floating list. `planePose`, `planeRelPos` and `propAngle` switch to it automatically.
- **Attitude limits**: the drone never rolls past `MAX_BANK` (50°, a hard clamp in `pathPose`) nor pitches past `MAX_PITCH` (20°). Bank follows `atan(v·ω / g)`, so the default paths are built from straights and constant-radius left arcs (R = 190 m) and the cruise speeds in `SPEED_KEYS` are kept near 36 to 42 m/s (the arcs reach about 47° of bank, 49.6° at the worst joint). The rail is 18° because the spline blend after release overshoots it by about 1° (19.0° measured). Tighter turns or faster cruising break `test/attitude.test.mjs`. The default arrays were generated by a small script (loop exit 40 m abeam, an inbound run starting about 720 m out, aimed at the ship), so edit them as data, or regenerate rather than nudge points.
- **Editable path**: the first two waypoints (`PATH_FIXED`) come from the catapult; everything after is `DEFAULT_PATH`, or a custom path from `localStorage['intercept.path.v1']` (`{points: [[x, alt, z], …]}`, validated by `validatePath`, altitude floor `MIN_ALT`). It is read **once at import**, so the path editor applies a change by saving and reloading.
- **Derived events**: everything is measured in the ship frame, so any path works:
  - `tLaunch` is the first moment the drone, having left `LAUNCH_RANGE`, closes back inside it. If it never leaves, launch is at the first closing moment after 8 s. If it never closes, launch is near the path's end.
  - Timeline markers "Turn back", "Close pass" and "Inbound run" come from prominent local maxima and minima of the range to the ship. They are not hard-coded.
  - `scenario.interceptMiss` is how far short the missile was before the hit is snapped on. The UI warns when it is large.
- **Missile**:
  - Proportional navigation is **simulated once at module load** into a fixed-rate sample table, starting from the tube mouth at `tLaunch` along the tube direction.
  - The last sample is snapped onto the drone, so the hit is exact. `tHit` is an output of that sim.
  - The launcher's slew (`launcherAim(t)`: stowed → aimed → stowed) is a pure function of `t`.
  - The drone is shot down on its **inbound run** (coming back at the ship), never while flying away. `tInbound` is the farthest point after the close pass, and `tLaunch` is derived as the moment the inbound drone closes inside `LAUNCH_RANGE`.
  - The `fwd` inbound run comes from ahead of the bow and the `aft` one from astern, so each launcher's missile leaves away from the ship. Keep it that way if you change a path.

### Rendering and timeline

- **Idle rendering and quality** (`main.js`): the loop always runs, but `renderer.render`/`labels.render` are skipped unless clock.t, the camera matrix (1e-5 tolerance), `rig.id`, the Director shot or the `invalidate()` counter changed (window capture-phase pointer/wheel/key/click/resize and every UI toggle bump it; the path editor always renders). `__scene.renderCount` counts drawn frames. Adaptive quality (`high`/`medium`/`low`, `?quality=` pins it, `__scene.quality`) is decided once from frame times between consecutive drawn frames, with at most one later step down; low halves the particles through `ParticleField.setDensity` (a golden-ratio index order plus `drawRange`, no re-bake).
- **A mission opens paused** (`clock.playing` starts false; Play or Space starts it; the app's own reloads, engagement Apply and the standby stepper, resume playing).
- **Deep links** (`share.js`): the Copy link button builds `?ship&mode&t&focus|cam=director` plus `#path=<base64url JSON>` for a custom path; `?t=` opens paused, `?focus=` focuses. `scenario.js` reads `#path=` before localStorage and never writes it (`scenario.sharedPath`). The URL is never touched while playing, and "Change ship" strips t/focus/cam/hash.

- `src/main.js` holds `applyTime(t)`, which poses everything for a given `t`, plus focus targets, picking and the render loop. `scenario.tEnd` is set here from the debris fall time. There is deliberately **no bloom pass**: the `Sky` shader outputs HDR values far above any usable threshold, so bloom turned the whole frame milky. Glow comes from additive sprites (flash, exhaust) instead.
- `src/labels.js` holds the floating tags (a `CSS2DRenderer` layer over the canvas, click-through) for the drone, missile and ship. `main.js` feeds it per-frame data from `applyTime`. The Labels button and the **L** key turn it off, and the choice is kept in `localStorage`. The ships carry no pennant number anywhere (tags, cards, hull paint): they are told apart by their launcher.
- `src/minimap.js` is the mini map: a translucent round radar, `--map-d` across (240 px on desktop screens, 150 px on phones and short screens; `minimap.js` and `maneuverMap.js` read it and re-measure on resize; on desktop the timeline is a narrower 820 px kept to the right) (`#minimap`). On every screen wider than a phone in portrait it sits beside the timeline panel on the bottom row (`body.has-map` moves the panel right by the map's width, so nothing floats over the scene); on a phone it floats just above the bottom sheet (`--tl-h` is set from the timeline's height by a `ResizeObserver`), centred on the ship with the bow up (screen up = +X, screen right = +Z, so the ship's frame is shown unrotated). It draws range rings, each drone (arrow along its world velocity, a cross once down), each missile (arrow, then an expanding ring at the burst) and their paths in the ship frame (faint for the whole path, bright for the part flown). Auto zoom picks the smallest of `SCALES` that holds everything with a 15 % margin; clicking cycles auto / 500 m / 1 km / 2 km. It redraws only when `t` or the zoom changed. The **M** key or the menu hides it (`localStorage['intercept.map']`); the editor and the folded interface hide it too.
- `src/trails.js` draws the trajectories as thick `Line2` lines in their own colours: ship track (green), drone (orange like the airframe), missile (cyan). Each is a faint dashed preview (30 % opacity) of the whole planned path with a solid overlay, in a muted slate-tinted version of its colour, on the part the object has already consumed (its `instanceCount` is a pure function of `t`, so scrubbing works both ways). The missile line shows from 1 s before launch. The Trails button and the **T** key belong to it (there is no colour legend: the tags and the map name each line), the choice is kept in `localStorage['intercept.trails']`, and the path editor hides the trails while it is open. `LineMaterial` needs `resize(w, h)` from `main.js`.
- `src/pathEditor.js` is the path editor (⋯ menu, **E** key). It pauses at t = 0 and shows the path as a cyan spline with draggable handles, altitude stems and a sea shadow, all in a group that follows the ship. Tools:
  - **Move**: drag a dot, double-click the line to add a point, Delete removes one, ↑/↓ change altitude.
  - **Draw**: freehand strokes on the sea at a chosen altitude, right-drag to orbit.
  - Copy and Paste as JSON, Default, Clear.
  - Also: numbered handles; the path coloured by altitude with direction chevrons; range rings (150, 400, 650 m = `LAUNCH_RANGE`) on the sea; stat tiles (length, flight time from `flightTimeForLength`, altitude range, closest approach); exact Ahead / Stbd / Alt fields for the selected point; snap to 10/25/50 m; **Shift-drag** a dot to change its altitude; `[` / `]` step through points; undo/redo (Ctrl+Z, Ctrl+Y, 100 steps; one step per drag, stroke or field gesture); whole-path tools (Smooth, Simplify = Douglas-Peucker at 12 m, Flip L/R, Wider, Tighter, Raise/Lower all).

  Edits are only a preview until "Apply & play", which stores them and reloads. Pointer handlers are registered on `window` in the capture phase so a handle drag never reaches OrbitControls. The editor's logic can be driven in Node with a stand-in DOM. `timeline.js` ignores shortcuts typed into number/text inputs and passes Ctrl/Cmd chords to `onKey` (and `main.js` drops them unless the editor is open), so typing a value or pressing Ctrl+R never triggers playback.
- **Interface** (`index.html`, `style.css`, `hud.js`, `layout-v.css`, `vtrack.js`): **the drone missions wear the drill's look and layout**: `main.js` adds `body.mission-maneuvers mission-drone`, so the drill's CSS (as for the formations mission) gives them the vertical timeline down the left on wide windows (`#vtrack`, built by the shared `src/vtrack.js`: `createVTrack({ events: scenario.events, tEnd, clock })`, names pushed apart with leaders, drag the rail or click a name; the horizontal bar is hidden then), the camera buttons in the strip at the top (`createCamStrip`, from 901 px), the compact playback panel at the bottom centre and the map at the bottom right; `src/layout-v.css` (imported by `main.js` only, scoped to `body.mission-drone`) puts back what the drill hides on purpose (Cinematic, Edit path, Missile engagement, units, Record, offline download), keeps the drill's grid and fullscreen hidden, hides the vertical timeline, strip, cards and panel while the path editor is open (`body.editing`) and the vertical timeline while the engagement panel is (`body.engaging`), and hangs the cards full width under the top bar on a phone in portrait. Layout observers (`--bar-h`, the vtrack's) do their work on the next animation frame: changing layout inside a `ResizeObserver` callback makes the browser report a "ResizeObserver loop", which `start.js` shows as fatal. The top bar is icons only (no brand: the chapter card names the launcher and mission). `#hud` holds the drill's slim see-through cards (`.mcard`, `.mh-*`), all from `t`: the **chapter card** (the last `scenario.events` label, the launcher and mission, a chip with the drone's state, a progress line through the chapter, `Next: <event> in <s>`, and a × that hides the cards like H), the **readout rows** (`.mh-cell`: range, with closing or opening speed, amber then red when an inbound drone is inside `scenario.launchRange`; relative bearing Green/Red from the bow with the altitude; speed; then the missile: time to launch and the range it fires at, Ready under 15 s, time to impact and range to target in flight, Hit; or the recovery: parachute countdown, descent rate, splashdown), and a range-to-ship sparkline card (`.hud-spark`, baked once, a cursor at `t`, dashed launch range; hidden on phones). The debrief card replaces them at the end (launch and intercept range, closest approach, peak speed; recovery: chute altitude, descent, splashdown range and bearing). Max G is the load factor |a − g|/g from after the booster. Speeds are km/h or knots (**U** or the ⋯ menu, `localStorage['intercept.units']`, shared with the tags through `labels.setUnits`), descent m/s. **C** (or Hide) hides the whole interface (`body.ui-hidden`, key `intercept.uiHidden`), **?** opens the shortcuts sheet, and Esc closes an open menu or sheet before freeing the camera. Phones keep the bottom-sheet timeline (portrait) and the single-row sheet (landscape). Panels sit at z 10–12, above the tag layer (z 5) and below the toast and error boxes. On phones and narrow windows the horizontal bar's labels are placed in pixels by `layoutMarkers` in `timeline.js`, and a label that doesn't fit is hidden (its tick stays). Check the drone scenes at 920, 1097 (a 1920 px screen at 175 %) and 1920 px wide and on a phone after changing the drill's layout CSS: they share it.
- `src/timeline.js` holds the master clock (`t`, play direction, speed) and the playback bar, markers and keys. The panel is compact on every screen wider than a phone in portrait (one control row plus the scrub bar). On desktop screens (at least 641 x 501) the chapter names stand above the bar, in up to four rows (`MAX_ROWS` in `layoutMarkers`), each tick with a stem up to its name; phones and short screens show ticks only, with the names in the tooltips and the skip buttons' titles. The skip buttons jump to the previous / next event (`clock.prevEvent()` / `nextEvent()`, keys `,` `.`); the speed is one button that cycles 0.1× to 4× (`clock.setSpeed`, `slower()` / `faster()`, keys `[` `]`, right-click goes back one). The clock is the only source of time.

### Director camera and sound

- **`src/director.js`** is the cinematic camera. The UI calls it **Cinematic** (button, **D** key, `?cam=director` or `?cam=cinematic`); the code still says Director. **It is the default view**: `main.js` turns it on at start unless a shared link names its own camera (`?focus=`, or `?cam=free`, which "Copy link" writes for a free camera). Each shot is a pure function of `t` that places the camera and its look-at point, so cuts land on the same frames when scrubbing or playing backwards. The shot list is derived from `scenario` times (catapult, chase, low close pass found by the "Close pass" event, launcher, missile ride, wide impact, splash; recovery swaps the last three for a parachute orbit and splash). A shot shorter than `MIN_SHOT` is dropped, so custom paths still get sensible cuts. It needs `dronePos(t, out)` to resolve to the wreck after impact (`dronePosAt` in `main.js`) and `tWater`.
- While directing, `main.js` bypasses `rig` and OrbitControls (`controls.enabled = false`; the polar limit would clamp the low shots) and sets the camera itself. Every manual camera input goes through `setFocus`, which ends the Director first and aims the orbit target level with the camera so there is no jump. Internal shot changes never call `setFocus`. Keep the field of view at 50: `pointScale` is only recomputed in `resize()`. Shot times can be checked in Node by standing in for `dronePos`.
- **`src/audio.js`** plays sound effects generated with the ElevenLabs connector (text-to-sound v2, prompts: one concrete sound each). `scripts/build-sounds.py DIR` (numpy, scipy, soundfile, ffmpeg) normalises them, turns the loops into seamless cross-faded PCM wavs (an mp3 loop can click at its encoder padding), and writes the base64 `src/audioAssets.js`, so the offline file needs nothing else. Loops (engine, motors, wind, surf, hum) run continuously; each frame the gain, low-pass, pan and playback rate (prop pitch, Doppler from analytic velocities, never frame deltas) are set from `t` and the camera. One-shots (catapult burst and clunk, launch, explosion, splashes) start at the sample offset `t - tEvent` and re-sync when time jumps; they play only while the clock runs forward. It is silent while time stands still. The context starts on the first user gesture (Sound button or **S** key; the choice is kept in `localStorage`). `window.__scene.audio.state` / `.loaded` report the context and decoded samples.

### Models

`src/models/` contains procedural geometry only, with **no external textures or assets**. Canvas textures are generated at load.

- **`kit.js`**: `Kit` collects parts per material and merges them, which keeps the detailed ship at a few dozen draw calls. Add new detail through a Kit, not as loose meshes. `hexa` builds sloped stealth blocks and auto-orients face winding. `slab` and `facePanel` place windows, doors and panels on sloped faces.
- **`ship.js`**:
  - The launcher stand and the pennant text depend on `SHIP_VARIANT` and `PENNANT`.
  - The hull is lofted from per-level lines (keel, bilge, waterline, knuckle, deck) with raked stems. Each level pair is a separate strip, so creases stay sharp.
  - Hull UVs flip *u* on the port side, and port and starboard use different halves of the texture, so the painted "920" reads correctly on both sides.
  - The animated parts are the radar, launcher yaw/pitch, tube cap, catapult cradle and flag.
  - The catapult follows the reference photos (a compact launcher: a plate about 5 x 3 m, a frame about 4.2 x 2.3 m, a beam about 4.4 m long): a bent stainless blast plate, angle-iron base frame, ladder-frame beam on tubular A-frame legs, rust-brown pivot ears, hydraulic strut, tie-down chains to deck sockets, plus a battery box and flight case. The ears sit outboard of the drone's body (|z| 0.62) and behind its wing, and the gas bottle and buffers keep a gap from it. After changing the rail pitch, length or ride height, re-check clearances by sampling `planePose` in the rail frame, as the Node check did.
  - Ship pick boxes live inside the ship group.
- **`parachute.js`** (recovery only): a red square ram-air-style canopy (an arched 5.4 m sheet, `archY`; its +Z follows the drone's heading) with 16 suspension lines along its edge and a pilot chute. Everything is a function of `t` and the drone's pose: lines pay out, the canopy streams then inflates, and after splashdown it collapses flat on the water downwind. The lines and pilot chute live in world space, and only the canopy has its own transform.
- **`engine.js`** (used by `plane.js`): the drone's engine, modelled on the reference photo: a horizontally opposed two-cylinder two-stroke with big finned cylinders and heads, a cast crankcase with a round magneto housing behind it, thick black spark-plug leads with silver elbow caps, a green carburettor on an angled manifold ending in a flared copper bell (it leans back over the fuselage roof), and, on the prop (`addFlange`, in the prop's frame so it spins), an orange anodised flange with four steel-blue bolts and a steel boss. It is added to the fuselage's `Kit`, so it breaks away with the fuselage (the direct-children rule below). `test/engine.test.mjs` checks its envelope. To look at a procedural model without a browser, render its triangles with a small software rasteriser (flat shading, z-buffer) that writes a PNG: the engine and the whole plane were checked that way.
- **`plane.js`**:
  - The fuselage and flying surfaces are lofted from rounded-rect and airfoil sections. Stations are evenly spaced, so painted detail isn't stretched.
  - The **direct children of `plane.group` are the debris pieces**: fuselage, wingL, wingR, tail, prop. Nest new detail inside them, or each addition becomes its own falling piece with its own splash.
  - Side lettering is drawn rotated ±90° in the canvas so it reads correctly from each side.
- **`environment.js`**:
  - `Sky`, also used as the PMREM environment.
  - Sun shadow frustum that follows the focus.
  - Sprite clouds.
  - Analytic ocean shader, kept deliberately simple so the frame rate stays high: a slightly choppy sea from five octaves of value noise with analytic gradients (`chopGrad`: features of about 48, 24, 12, 6 and 3 m, each octave rotated and drifting slowly its own way at `CHOP_DRIFT`, about equal slope per octave `CHOP_SLOPE`, the drill 60 % of it, each octave faded by its pixel footprint `fwidth` before it shimmers; the surface stays flat, only the normals ripple; not sine waves: long swells rolling under the moving ships looked dizzying, and a few crossed sines read as parallel bands or a crosshatch), a sky gradient reflected by Fresnel, the sun's glitter, a cheap two-sample-noise wake (`uShipX`), fog. No noise textures, no environment lookups. (A heavy WebGPU FFT ocean and a PBR-style shading were tried and removed: they cost 5 to 10 times the frame time on integrated graphics.) Its wake foam reads `uShipX`, and `hullHalf()` there mirrors `widthFactor()` in `ship.js`.

### Mission looks, scenery and weather

`createEnvironment(renderer, scene, { look })` gives the drone missions, Fly and the duel their own world (the drills and Solo Air Defense keep `calm`, and `calm` and the default render exactly as before: checked pixel for pixel against the old module).
- `src/looks.js` is the pure table (Node test `test/looks.test.mjs`): `LOOKS` (`intercept` golden hour with haze, `chute` clear morning, `fly` clear day with scenery and low clouds, `duel` grey and rough), `todAt(elev)` (one sun elevation drives the sky, haze, fog, sun and fill light, water tint and cloud tint), `WEATHER` (`clear`, `haze`, `squalls`, `overcast`), `resolveLook(name, weather)`, and `fromDisplay` / `aces` (design a colour as the sRGB a viewer should see and solve it back to the scene colour the ACES tone mapping needs; exposure 0.75 in every mission). A look's dome is drawn in display space with no tone mapping (blending a warm horizon and a blue zenith before the tone curve turned the sky pink); the sea's fog and `scene.fog` use the matching scene-space colour, so the horizon has no seam. The physical `Sky` is only the image-based light.
- Weather: `?weather=` or `localStorage['intercept.weather']`, read once; the More menu's Weather entry (`src/weatherButton.js`) cycles Auto / Clear / Hazy / Squalls / Overcast and reloads; Copy link carries it. Weather changes fog distances, overcast, sea state and the sprites drawn.
- The ocean shader gained `uSea` (wave steepness, and bigger lumps above 1), `uWind` (a drift added to every octave, which stay rotated), `uCaps` (whitecaps from the slope already computed, no new octaves, faded by pixel footprint), `uGlitter`, `uReflect`, `uFoamTint`; their defaults reproduce the old sea.
- `src/scenery.js`: world-fixed islands (heightfields, 3.5 km or more out), distant merchant ships, instanced buoys (Fly only, a speed cue near the water), rain squalls and low cloud banks. `env.follow()` re-places them around the camera (the wrap period is at least twice the fog distance, so they only jump while fogged out); the scripted missions never call `follow`, so there they are simply fixed.
- `src/fx/shipFx.js`: funnel haze and bow spray, baked for the scripted missions (`createShipFx`, a pure function of `t`), emitted live by `ShipPlume` through `liveFx.funnelSmoke` / `bowSpray` for Fly and the duel (particle mode `FUNNEL`). The drills do not get them.

### Effects, camera and picking

- **`src/fx/particles.js`** is a `ParticleField`. Each particle's position and colour are closed-form in `uTime - birth`, with all births baked at load.
- **`src/fx/effects.js`**:
  - **Debris**: closed-form linear-drag ballistics from each part's pose at `tHit`, then the parts sink.
  - **Recovery**: a puff as the pilot chute pops, then at splashdown a spray burst and an expanding foam ring.
  - **Particle bake**: booster plume and deck blast, drone exhaust haze, launch backblast, missile trail, fireball, burning smoke and splashes. Anything emitted from the ship must add the ship's velocity.
- **`src/cameraRig.js`** eases to a target, then carries the camera by the target's per-frame delta. Focus targets always resolve to a position:
  - The missile sits at its tube before launch, and the blast point after.
  - The drone hands over to its falling fuselage after impact.
  - Focus switches from the missile to the wreck at `tHit`.
- **Picking**: drone and missile pick spheres grow with camera distance and win over the ship's boxes.
